## What SecretCsv is

SecretCsv is a standalone WinUI 3 / .NET 10 desktop app: an offline,
CSV-driven data store with a CRUD UI. Point it at a CSV, it imports the
records; from there you can browse, search, add, edit, delete, print, and
export by hand — no network access, ever, at any point.

It is the successor to a project called SecretLead, which attempted the same
idea but with a separate `schema.md` file declaring field names and roles.
SecretCsv drops that entirely: **the CSV's own header row is the schema.**
No second file, no separate grammar to maintain, no "does this CSV match the
schema" validation step.

## Core design decisions

- **No schema file.** Whatever columns are in the CSV header row are the
  fields. Nothing is declared elsewhere.
- **Role by position, not declaration.** The CSV's first column plays the
  "Category" role (top-level grouping). The second column plays the
  "Nickname" role (the searchable identifying field for browsing). This is
  fixed by column order, not configurable per import.
- **Storage is keyed by CSV filename.** Importing `contractor.csv` creates
  (or appends to) a `Contractor.txt` record store. Importing a
  differently-named CSV creates a separate store. This preserves SecretLead's
  "existence-of-file is the mechanic" approach without needing a schema to
  name the entity.
- **Field normalization is substring-based on column header text**, same
  rules as before: any header containing `date` reformats to `mm/dd/yyyy`;
  any header containing `phone` strips to digits and reformats by digit
  count; any header containing `email` is left untouched.
- **Manual CRUD (Add/Edit/Delete) uses whatever fields were last established**
  for that store — i.e. the column set from the most recent CSV import into
  it. A store with no import yet has no fields to add a record with, so
  Add is disabled until at least one CSV has been imported.

## Non-negotiables

- No third-party NuGet packages beyond the Windows App SDK — .NET BCL and
  Windows App SDK / COM only.
- No network calls, no scraping, no telemetry. Offline-only, always.
- **Packaged MSIX from day one** — this is not optional and not deferred.
  Unlike SecretLead, this project does not have an unpackaged fallback mode.
- Use `Windows.Storage.ApplicationData.Current.LocalFolder` for the record
  store. Do **not** use `Environment.GetFolderPath` as a workaround — that
  pattern existed in SecretLead only because it lacked package identity.

## Packaging — lessons paid for the hard way (do not relitigate these)

- `PublishTrimmed` must always be `False`. The `dotnet new winui` template
  defaults this to `True` for Release builds — that default is wrong for
  this project and must be overridden. Trimming crashes WinUI 3 /
  Windows App SDK apps at startup (`combase.dll`).
- Confirmed-working toolchain versions (tested clean launch on WIN11DEV,
  2026-08-02): `Microsoft.Windows.SDK.BuildTools` `10.0.28000.2526`,
  `Microsoft.Windows.SDK.BuildTools.WinApp` `0.5.0`,
  `Microsoft.WindowsAppSDK` `2.3.1`. Don't downgrade these without retesting
  on a clean machine.
- Self-contained, packaged deployment is the target:
  `WindowsAppSDKSelfContained=true`, no `WindowsPackageType=None` override.
- Every code or config change gets tested with a real packaged install on
  WIN11DEV (a clean machine, not the dev machine) before being trusted.
  `dotnet run` on the dev machine proves it compiles and launches with
  package identity locally — it does not prove it works on a clean install.
